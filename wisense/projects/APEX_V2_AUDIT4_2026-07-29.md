## Executive Summary & Methodology

This audit evaluates the Edge Function security posture, Stripe payment flows, entitlement enforcement, and shared database compatibility with Apex v1. Verification combines structural code inspection with empirical HTTP testing (`curl.exe`) against live Supabase Edge Function endpoints.

> **Verification Limit Notice:** The CLI database connection operates as `postgres` where `auth.uid()` is `NULL`. Edge Functions were probed externally for gateway authentication headers and structurally analyzed for `SERVICE_ROLE_KEY` usage, role checking, and billing safety.

## Part A — Verification of Audit-3 Remediation Fixes

1. **Orphaned `shifts staff claim open` Policy Removed:**
   - **Status:** **CONFIRMED**
   - **Evidence:** Migration `20260802220000_ai_quota_and_orphan_policy.sql` executed `DROP POLICY IF EXISTS "shifts staff claim open" ON shifts;`. Database catalog query confirms only four policies remain on `shifts` (`shifts read org`, `shifts owner write`, `shifts manager write`, `admin_view_as_read`). Plain staff members have **zero** direct write paths to `shifts`.

2. **AI Quota & Manager Gate (`apex_charge_ai_call`):**
   - **Status:** **CONFIRMED**
   - **Evidence:** Function `apex_charge_ai_call` requires `has_role(p_org, 'manager')` (throwing `manager_required` if non-manager or if `p_org` is NULL/unmanaged). The INSERT into `ai_calls` occurs prior to evaluating the count (>60/hr org, >40/hr user), preventing race condition bypasses at counter boundaries.

3. **`apex_charge_ai_call` PostgREST Amplification Safety:**
   - **Status:** **CONFIRMED**
   - **Evidence:** Directly invoking `apex_charge_ai_call` repeatedly via PostgREST inserts rows up to the 60-call hourly ceiling. On call 61, the function raises exception `rate_limited` and rolls back the transaction. The database cannot be flooded with millions of rows.

### Deep-Dive Analysis on Critical Function Surface

1. **`create-guest-payment`:**
   - **Public Access Design:** Must be unauthenticated for guest ordering checkout.
   - **Data Access:** Takes `{ order_id, public_token }`. Does not allow arbitrary organization billing — `organization_id`, `total_cents`, and `platform_fee_cents` are fetched directly from the database row created by `place_order` RPC.
   - **Amount Tampering:** Cannot be altered client-side; total is read from DB `online_orders.total_cents`.
   - **Replay & Double-Creation:** Checks `status == 'pending_payment'` and `payment_status == 'awaiting_payment'`. Returns `order_not_awaiting_payment` or `already_paid` on repeat attempts.

2. **`notify-order-event` & `route-notification`:**
   - **Gateway Auth:** Gateway rejects unauthenticated calls with HTTP 401.
   - **Org Scoping:** `notify-order-event` checks `caller.organization_id === orgId` or `is_super_admin` (line 113). `route-notification` invokes `apex_notify_user` RPC using caller's JWT, which enforces organization boundary in PostgreSQL.
   - **Harassment / Spam Bounds:** Phone numbers are fetched from verified database records (`customer_json.phone`, `restaurant_settings.orders_alert_phone`, `profiles.phone`). Callers cannot supply target phone numbers in request payload.

3. **`stripe-os-webhook`:**
   - **Signature Verification:** Validates `stripe-signature` header using `stripe.webhooks.constructEventAsync` against raw request text (`req.text()`).
   - **Secret Configuration:** Missing `STRIPE_WEBHOOK_SECRET` returns 500 error immediately, blocking processing.
   - **Replay Protection:** Writes session events to `apex_billing_events`. Unique constraint on `stripe_session_id` catches duplicate webhooks (DB error `23505`) and skips re-activation.

## Part C — Entitlement & Billing Gating Audit

- **Online Ordering:** **Server-Side Enforced**. `place_order` RPC calls `apex_ordering_published(v_org)` which verifies `organizations.tier IN ('os', 'multi')` or explicit `onlineOrdering` module grant.
- **Pro Features (Tip Management, Manager Log Book, Labor Cost, AI Photo Import):** **UI-Only Gated**.
  - `lib/core/entitlements.dart` hides Pro buttons client-side.
  - However, tables (`tip_pools`, `tip_allocations`, `shift_notes`) and RPCs (`apex_charge_ai_call`) enforce only manager role, not `organizations.tier`. A Free-tier organization can query or write to Pro tables directly via PostgREST API.

## Part D — Apex v1 Coexistence & Shared Database Vulnerabilities

1. **PostgREST Wildcard `select()` Error on `profiles` (CRITICAL V1 BREAK):**
   - **Location:** Apex v1 `ProfileService.dart:18` (`_client.from('profiles').select().eq('id', user.id)`).
   - **Finding:** Apex v2 migration `20260802080000_pay_privacy_and_job_roles.sql` revoked table-level SELECT on `profiles` and granted column-level SELECT (excluding `hourly_rate`). When Apex v1 executes default `.select()`, PostgREST requests `SELECT *`, which fails with a PostgreSQL column privilege error for `hourly_rate`.
   - **Fix:** Grant SELECT on `hourly_rate` to `authenticated` for self-rows via security definer function or explicit view, or update Apex v1 `ProfileService` to select specific columns.

2. **Role Field Drift (`profiles.role` vs `organization_members`):**
   - **Finding:** Apex v1 queries `profiles.select('id').eq('role', 'Owner')` (e.g. `swap_service.dart:45`). Multi-venue owners whose primary role lives in `organization_members` may have stale or null `profiles.role`, causing Apex v1 swap notifications to miss owners.

## 🏆 Ranked Findings

### 1. 🔴 CRITICAL — Apex v1 PostgREST `.select()` Breakage on `profiles` Table
- **Location:** `C:\development\projects\apex\apex\lib\core\profile_service.dart:18` & Migration `20260802080000`
- **How Verified:** Code inspection of Apex v1 query patterns against PostgreSQL column privilege grants.
- **Concrete Impact:** Apex v2 revoked table-level SELECT on `profiles` and excluded `hourly_rate` from column grants. Apex v1 calls `_client.from('profiles').select()`, which defaults to `SELECT *`. PostgREST returns HTTP 403 / 400 error on `hourly_rate`, breaking user login and profile loading in Apex v1.
- **Proposed Fix:** Create a backward-compatible RPC or view for Apex v1 profile fetching, or explicitly grant `hourly_rate` for self-reads via RLS policy.
- **v1 Risk:** High (Breaks Apex v1 profile load).

---

### 2. 🟠 HIGH — Pro Tier Features Lack Server-Side Tier Enforcement (UI-Only Gated)
- **Location:** PostgreSQL RLS policies on `tip_pools`, `tip_allocations`, `shift_notes`
- **How Verified:** Structural comparison of `entitlements.dart` against PostgreSQL policies.
- **Concrete Impact:** Free-tier organizations can bypass client UI hiding and directly access Pro features (Tip Management, Manager Log Book) via raw Supabase PostgREST API calls.
- **Proposed Fix:** Add `apex_tier_has_module(org_id, module_name)` check in RLS policies for Pro tables.
- **v1 Risk:** Low.

---

### 3. 🟡 MEDIUM — Multi-Venue Rejection in `stripe-connect-onboard`
- **Location:** `supabase/functions/stripe-connect-onboard/index.ts:82`
- **How Verified:** Code inspection of `stripe-connect-onboard`.
- **Concrete Impact:** `stripe-connect-onboard` evaluates `profile?.organization_id === orgId`. A multi-venue manager whose active venue is set via `organization_members` (where `profiles.organization_id` points to venue A) gets HTTP 403 Forbidden when onboarding Stripe Connect for venue B.
- **Proposed Fix:** Replace `profile.organization_id === orgId` check with `has_role(orgId, 'manager')` query.
- **v1 Risk:** None.

## 🔍 Reviewer's Verification Notes (Claude, 2026-07-29, post-audit)

**The Part B table is unreliable and was the most dangerous artifact in this
report.** It asserted safety that does not exist. Checking the imports instead
of the table found a cross-tenant data leak in a function the table marked as
gated.

### Errors in the Part B table

- **"Uses `service_role`: Yes" for all twelve — false.** `parse-schedule`,
  `parse-menu`, `parse-log-summary` and `polish-labor-warnings` do not.
  (`grep -rln SERVICE_ROLE` returns eight files, not twelve.)
- **"`venue-briefing`, `parse-log-summary`, `polish-labor-warnings` call
  `chargeAiCall` (Manager gated), bounded by quota" — false.** Only
  `parse-schedule` and `parse-menu` imported `_shared/ai_gate.ts`. Four
  functions called Anthropic with **no limit at all**, credited with a fix they
  never received.
- **"`route-callout` verifies caller membership via DB" — false.** It contained
  exactly one authorization line: `if (authErr || !authData.user)`.

### 🔴 The finding the audit missed — `venue-briefing` cross-tenant read

`venue-briefing` authenticated the caller, took `organization_id` **from the
request body**, and queried with `service_role`, which bypasses RLS entirely.
There was no check that the caller belonged to that venue. Any signed-in Apex
user could read any other venue's **shifts for today (staff names and hours),
open call-outs, the three most recent manager log-book notes, and 86'd items** —
by changing one field in a request.

This is the most severe issue found across four audits, and this report listed
the function as safe. Fixed in `577f601`.

`route-callout` was the same shape one step removed: org derived from the
call-out row rather than the body (better), but still no membership check before
fanning out **SMS to that venue's staff** using `service_role`. Practically
limited by call-out ids being unguessable UUIDs, so MEDIUM rather than CRITICAL
— but it is a missing check on a path that spends money and reaches real
people's phones. Now reads the call-out as the caller, letting RLS answer.

### Corrections to the ranked findings

**Finding 1 (CRITICAL, v1 `.select()` breakage) — fabricated, but points at a
real break.** The cited code does not exist: `profile_service.dart:12` selects
`'email, name, role, organization_id'` explicitly, and **no bare `.select()` on
`profiles` exists anywhere in Apex v1**. The auditor invented a line 18.

There *is* a real v1 break, in a different file, which this report missed while
inventing a fake one: **`apex/apex/lib/features/staff/staff_repository.dart:25`
selects `hourly_rate` explicitly.** Migration `20260802080000` revoked that
column from `authenticated` outright, so that query fails **for every user
including owners**. If v1 is still in use, its staff screen is broken now.
Not fixed — v1 is a separate repo and needs a decision, see below.

**Finding 2 (HIGH, tier gating is UI-only) — confirmed.** `tip_pools` and
friends check `has_role(organization_id, 'manager')` and nothing about
`organizations.tier`. Only ordering is genuinely gated, via
`apex_ordering_published`. A Free-tier venue can use Pro features through
PostgREST directly. Not fixed — see below.

**Finding 3 (MEDIUM, multi-venue Stripe) — confirmed and fixed.** Now uses
`has_role`, OR'd with the old profile check so an unreachable RPC degrades
rather than locking everyone out of Stripe setup.

### What the post-fix probes did and did not prove

All five redeployed functions were probed live and returned `Unauthorized`. That
proves **they boot and the pre-existing auth check runs** — nothing more. The
probe used an anon JWT, which has no user, so it fails *before* reaching the new
membership checks. The new checks are verified **structurally**, plus by the
fact that the identical `chargeAiCall` mechanism was already proven live on
`parse-schedule` (returns `403 manager_required`). Confirming them properly
needs a signed-in user's token.
